The project is **well advanced** and not a mock. Ground truth (run now):

Between the 5 October audit and the 6 October completion report the project moved from a "prototype MVP" to a **working Alpha with Soroban contracts deployed on Testnet**. Most of the completion report's claims are **true in the code** (verified file by file).

**Core conclusions:**
- The product is **technically strong** for the scope it chose: a full financial lifecycle, deployed contracts, reconciliation, indexing, wired to public documentation.
- What is missing to be a "complete, respected product" falls into three buckets:
  1. **In-code gaps closable now** (notably: the sandbox is not interactive, provider integrations are not wired to the ledger, observability/CI, some stubs).
  2. **Security gates** (independent audit, enforced multisig, HSM key custody, storage tested against a real bucket).
  3. **Regulatory/commercial gates** (licence or licensed partner, legal opinion, custody, payment rails, real traction) — **code cannot close these**.
- **The sandbox is not ready:** what exists is a static illustration page (`/sandbox`) plus an interactive Demo mode. There is no real interactive sandbox. Details and plan in section 6.

## 6. Sandbox assessment + interactive build plan

> **The ready-to-execute detailed design (data model, engine, API routes, screens, acceptance criteria):** `docs/sandbox-interactive-plan.md`.

### 6.1 Is the sandbox ready? — **No**

Three things get confused:

| Name | What it actually is | Interactive? | What it does |
| --- | --- | --- | --- |
| `/sandbox` ("Partner sandbox") | A static illustration page | ❌ | 6 hand-written scenarios run through the waterfall engine `lib/finance/scenarios.ts`. No execution, no wallet, no chain, no state that changes. |
| Demo mode | A real app with seeded accounts (`demo123`) + virtual ledger `lib/simulation/ledger.ts` | ✅ | A full financing cycle on the default Prisma ledger (SimWallet). It changes real state in a shared database. |
| Provider "sandbox" integrations | Sumsub/Transak/Circle adapters | ⚠️ | Return 503 "ready in code but needs a sandbox key". `INTEGRATION_MODE` in `.env.integrations.example` does not move the ledger. |

**Verdict:** what exists = **a static illustration page + a shared Demo environment**, not a sandbox. The problem with Demo is that it is **shared**: any visitor affects the data everyone sees, with no isolated session or reset.

### 6.2 What makes a sandbox "real"?

| Requirement | Description |
| --- | --- |
| Isolation | Each visitor has an isolated space (session/tenant) — no touching the shared Demo data |
| Reset | A "reset" button returns the session to its initial state |
| Seed data | Facilities/pools ready to exercise any path immediately |
| Role play | Switch between SME/investor/underwriter/operations/supplier within one session |
| Time travel | Fast-forward installments and default (the simulation clock exists) |
| Scenario injection | Normal / early settlement / default / supplier failure / insurance event |
| Evidence | Download a "proof pack" (receipts, positions, reconciliation report) |
| Guardrails | "No real money" banner + rate limiting + no real personal data |
| Chain proof | Real Testnet links where applicable (keeping money inside the sandbox ledger) |

### 6.3 Architecture options (with recommendation)

| Option | Description | Pros | Cons | Effort |
| --- | --- | --- | --- | --- |
| **A — Isolated simulation (recommended for phase 1)** | A session-isolated sandbox reusing `lib/simulation/ledger.ts` + `lib/lifecycle/service.ts` on a temporary "tenant" (separate SQLite/Postgres schema or a `sandboxId` namespace) with a simulation clock | Reuses existing code, safe, fast, no keys | Not a real chain | Medium |
| **B — Ephemeral Testnet tenant** | Each session gets a temporary Stellar keypair + Friendbot + real execution on contracts v3, with periodic cleanup | Fully "real" | Heavier; key/cleanup/cost management and abuse risk | Large |
| **C — Hybrid** | Phase 1 = A; phase 2 = a "run the same scenario on Testnet" button linking to server-managed execution | Safe progression | Extra complexity | Large |

### 6.4 Proposed implementation plan (phases)

**Phase 0 — design decisions (half a day):** isolation scope; anonymous session or login; launch scenarios; retention and reset.

**Phase 1 — isolated simulation sandbox (1–2 weeks):**
- Session layer (`sandboxId` in a cookie) + a namespace in the ledger or a separate schema.
- Reset endpoint + scenario seed.
- An interactive UI replacing the static `app/sandbox`: a lifecycle stepper + live financial/asset/chain state panels.
- Role switcher + simulation clock (exists in `lib/simulation`).
- Inject the six existing scenarios from `lib/finance/scenarios.ts` as runnable events.
- Guardrails: rate limit (`lib/security/rate-limit.ts`) + legal banner.

**Phase 2 — evidence and proof (3–5 days):** a downloadable proof pack (receipts, positions, reconciliation report) + real read-only Testnet links.

**Phase 3 — (optional) ephemeral Testnet:** real execution on contracts per session + cleanup.

**Acceptance criterion:** a visitor can, without an account and without real money, run a facility from creation to recovery, reset it, and download the state evidence — without affecting any other visitor's data.
